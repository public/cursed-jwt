# Simplifying cursed-jwt

Where the lines are, what can go without costing speed or correctness, and what was tried. Measured on `main` at
1e0fafb (2026-11-01). The Xeon is the Platinum 8260 behind the broker (Cascade Lake, AVX-512, no SHA-NI), and its
numbers decide.

What the inventory shows:
- **Generated code is 55% of the repo** (fiat-crypto plus OpenSSL's asm). Neither is hand-maintained, and both
  have a script that re-derives them.
- **The SHA-256 lane abstraction already exists.** `jwt_mb.inc` is one ISA-agnostic template; each ISA supplies about
  15 macros. Scalar, NEON, AVX2, AVX-512VL, the 2×ymm pairs and zmm are all instantiations of it. The remaining
  per-ISA code is load/transpose/store glue, which differs between ISAs. Another layer would not shrink it.
- **Two opt-in JSON parsers (442 lines) are slower than the default** on the Xeon, by their own documentation.
- **Two engines lose at every batch size on the Xeon:** the 2×ymm 16-lane AVX2 and AVX-512VL pairs (README:
  176 vs 154 ns at batch 16 and 32; 2.80 vs 2.43 and 1.66 vs 1.34 cycles/byte measured). Dispatch never picks
  them, and no consumer calls them.
- **The three group drivers repeat the same plan-and-sort loop** (`MB(drive)`, the 16-lane driver, `ce_drive_x`).
- **Dead knobs.**
  - `JWT_ES_ILV` gained nothing on either machine (exp144).
  - `JWT_SHA2_STREAMS` has the same default as `jwt_hmac_sha2_4`, which is an alias of the default.
  - The `JWT_*_MIN_LANES` overrides are undocumented.
- **The PK rules in the Makefile are 16 copies of one rule** with different flags.
- **The test harnesses overlap on purpose.** HS256 is checked against OpenSSL (differential), Python's `hmac` (the
  tokens), pyca/cryptography (random vectors), RFC/NIST/Wycheproof (fixed vectors), an independent Python model under
  Hypothesis, and libFuzzer with OpenSSL re-signing. Each is a different oracle, so none is a duplicate to remove.
  `test_cases` is already table-driven (macros over literal payloads).
- **Consumers** (the challenge submission, which vendors the library, and the nginx/Envoy/HAProxy branches) call
  `jwt_key_init`, `jwt_verify_batch`, `jwt_verify_batch_scalar`, `jwt_b64url_decode{,_scalar}` and
  `jwt_engine`. Nothing below removes or changes any of those.

Options 1–3 together remove 812 lines of non-vendored code (9,086 → 8,274, −9%). None of them changes a default code
path: 1 removes code the default build never compiled, 2 removes engines dispatch never picks, and 3 leaves the
x86-64 object code byte-identical.

**What the Xeon taught:** at this size, gcc's code layout moves RS256 and HS256 batch 1 by 1–3% whenever the text in
front of them shifts. Two harmless-looking changes (2b, 3b) failed parity for that reason alone. A change to the
library is not "free" until it has run on the Xeon against `main` in the same run, with `main` twice as a control.

## Prototypes

Each is a draft PR from `main`, independent of the others. Tests run on each:
- `make test-quick test-vectors asan pk-test pk-asan fuzz-smoke test-hypothesis` on macOS arm64 (Apple clang);
- `scripts/docker-test.sh amd64 test-quick test-vectors asan avx512 pk-test fuzz-smoke` on Linux amd64, gcc 13 and
  clang 18;
- the HS256 suite with RFC 4231 / NIST CAVP / Wycheproof vectors on the Xeon, on the AVX-512VL and zmm engines, plus
  RS256/ES256/EdDSA vectors for option 3.

Xeon experiments:
- exp1359: the first A/B of all three branches against main;
- exp1360: the test suites on AVX-512 hardware;
- exp1363: the layout split of option 2;
- exp1364: the recheck of option 3.

Each PR's description has its numbers.
